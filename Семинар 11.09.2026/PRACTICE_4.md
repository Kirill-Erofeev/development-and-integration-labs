# Практика 4 — модульные и интеграционные тесты

## Требование и реализация

Тесты разделены по контрактам: `tests/test_predict.py` проверяет CLI и входные
данные, `test_output_format.py` — JSON/text, `test_model_service.py` — артефакт
и метаданные, `test_api.py` — FastAPI через `TestClient` и lifespan.
Положительный сценарий с сохранённой моделью дополняет синтетические fixtures.
Обучение внутри HTTP-запросов не допускается.

## Запуск

```powershell
py -3.11 -m pip install -r requirements.txt
py -3.11 -m pytest -q
py -3.11 -m pytest -q tests/test_api.py tests/test_model_service.py
```

Первый прогон является полным для этого этапа; второй полезен при адресной
диагностике. В CHECKS.md фиксируется фактическое число тестов и код завершения,
без переноса чисел из другой версии проекта.

## Проверяемые инварианты

- `/health` и `/predict` используют один загруженный объект модели.
- Несколько запросов не вызывают повторный `load` или `fit`.
- Порядок ключей JSON не меняет порядок признаков estimator.
- Явно переданный путь модели имеет приоритет над `ML_MODEL_PATH`; затем работает
  переменная окружения и стандартный путь.
- Пропуски, лишние поля, неверные типы, неположительные и неконечные значения
  отклоняются с `422`, повреждённая или отсутствующая модель останавливает startup.
- OpenAPI описывает действующие поля `prediction`, `class_name`, `model_ready`.

`TestClient` подтверждает контракт приложения в процессе теста. Отдельный HTTP-запуск
и контейнерный запуск являются другими проверками и не считаются выполненными
только по успешному pytest.
