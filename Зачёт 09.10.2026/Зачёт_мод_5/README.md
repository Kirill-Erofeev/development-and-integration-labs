# Предзачётная практическая работа: развитие ML API

Каждый студент получает вариант из папки `Вариант_1`–`Вариант_4` согласно файлу `Распределение_вариантов.md`.

В каждом варианте есть:

- `notebooks/source_experiment_updated.ipynb` — обновлённый исходный эксперимент с первой частью функции;
- `notebooks/new_functionality.ipynb` — отдельный эксперимент со второй частью функции;
- `frontend/index.html` — готовая клиентская страница; её нужно перенести в репозиторий и отдавать тем же FastAPI-приложением;
- `Задание.md` — индивидуальное ТЗ и описание работы страницы.

Ноутбуки служат проверяемым эталоном входных и выходных данных. Код из них нужно выделить в модули проекта, не оставляя бизнес-логику только в Jupyter. Конкретные имена модулей могут отличаться, если в README описана их роль.

## Общие условия сдачи

1. Основа — собственный репозиторий из практик 1–4 с Iris-моделью. Если API ещё не создан, его требуется создать на FastAPI.
2. Реализовать все endpoint'ы своего варианта, их Pydantic-схемы, обработку некорректного запроса и HTTP-коды.
3. Перенести оба фрагмента функциональности из ноутбуков в код проекта. Ноутбуки сохранить в `notebooks/` как воспроизводимые эксперименты.
4. Дополнить `README.md`: назначение функции, запуск, таблица endpoint'ов, примеры запросов/ответов, запуск тестов и описание фронтенда.
5. Добавить минимум пять новых тестов: прикладная логика, успешные и ошибочные запросы API, а также проверка статической страницы.
6. Положить страницу в каталог статических файлов (например, `static/index.html`) и отдать её с того же приложения по `GET /`. Ajax-запросы должны быть относительными (`/predict`, а не `http://localhost:8000/predict`), поэтому CORS не нужен.
7. Не менять обученную модель ради задания: оценивается качество интеграции, контракта, тестов и документации.
8. Создать запрос на слияние (MR) своей рабочей ветки в основную и назначить ревьюером одногруппника, которому выдан **другой** вариант задания. В MR должны быть осмысленные название и описание; после ревью нужно ответить на замечания или обосновать их неприменимость.

> Подсказка по GitVerse: ревьюером можно назначить только соавтора проекта. Сначала добавьте выбранного одногруппника через свойства проекта в список участников/соавторов и выдайте ему право на запись, затем на странице MR выберите его в блоке «Ревьюеры». Актуальная инструкция: [совместное ревью в GitVerse](https://gitverse.ru/docs/collaborative/repositories/guides/pull-requests/collaborative-review/).

## Демонстрация

Показать запуск приложения, страницу `http://127.0.0.1:8000/`, один успешный и один ошибочный сценарий, `/docs`, тесты, изменения в README и созданный MR с назначенным ревьюером. Все новые изменения оформить осмысленными коммитами.
