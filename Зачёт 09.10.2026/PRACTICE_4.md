# Зачёт — вариант 4

## Требование и реализация

Проект расширяет существующий Iris API паспортом сохранённой модели, UUID
запросов и предоставленной страницей. Ветка — `course/exam-4`.
Обученный артефакт и вычисление предсказания сохранены; повторное обучение
демонстрационного notebook не переносится в runtime.

Паспорт реализован в `src/model_service.py`, UUID и события — в `src/request_id.py`,
маршруты и middleware — в `app/api.py`, контракты — в `app/schemas.py`.
Страница находится в `static/index.html`, рабочие notebook — в `notebooks/variant4/`.
Они используют общие модули; исходные материалы преподавателя сохраняются отдельно.

## Запуск и контракт

Модель и CLI сохранены. HTTP-контракт изменён: `prediction` заменено на `class_id`,
`model_ready` — на `model_loaded`. Новый `request_id` связывает запрос, ответ и лог.
Клиент, smoke-проверка, healthcheck Compose и OpenAPI согласованы с этим контрактом.

```powershell
py -3.11 -m uvicorn app.api:app --host 127.0.0.1 --port 8000
```

Веб-страница: <http://127.0.0.1:8000/>; Swagger UI: <http://127.0.0.1:8000/docs>.
Модель загружается в lifespan; `ML_MODEL_PATH` позволяет выбрать доверенный артефакт.
При ошибке его загрузки запуск останавливается.

| Операция | Успешный ответ |
| --- | --- |
| `GET /` | HTML-страница с паспортом модели и формой |
| `GET /health` | `{"status":"ok","model_loaded":true}` |
| `GET /model-info` | `model_type`, `classes`, `feature_count`, `model_loaded` |
| `POST /predict` | `class_id`, `class_name`, `request_id`; заголовок `X-Request-ID` |
| `GET /openapi.json` | Схема нового контракта |

В другом терминале:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/model-info | ConvertTo-Json
$headers = @{ 'X-Request-ID' = 'e21f05a0-837f-4ea9-84a0-621ce8f8b0a8' }
$body = '{"sepal_length":5.1,"sepal_width":3.5,"petal_length":1.4,"petal_width":0.2}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/predict -Headers $headers -ContentType application/json -Body $body | ConvertTo-Json
py -3.11 scripts/check_api.py --base-url http://127.0.0.1:8000
```

Ожидаются `class_id: 0`, `class_name: "setosa"` и отправленный UUID.
Корректный UUID канонизируется; отсутствующий, пустой или неверный заголовок
заменяется новым UUIDv4. Для `/predict` идентификатор назначается до валидации:
он возвращается также в предусмотренных ответах с ошибками и в `X-Request-ID`.
Тело запроса требует четыре положительных конечных числа без лишних полей.
Ошибки полей или синтаксиса JSON дают `422`, некорректная кодировка тела — `400`,
неготовая модель — `503`, ошибка прогноза — безопасный `500`.

Паспорт раскрывает только `LogisticRegression`, имена трёх классов,
число признаков `4` и готовность. Пути, содержимое pickle и обучающие строки
не возвращаются. В журнал пишется `prediction_completed` с UUID и именем класса;
ошибки дают `prediction_rejected` или `prediction_failed` с UUID и HTTP-статусом.
Исходные признаки и некорректный заголовок не записываются.

## Демонстрация страницы и UUID

1. Запустить API и открыть `/`. Убедиться, что видны тип модели, три класса,
   четыре признака и признак загрузки.
2. Отправить контрольные признаки `5.1`, `3.5`, `1.4`, `0.2`.
   Браузер создаёт UUID и отправляет его в `X-Request-ID`; результат должен
   содержать класс `0`, имя `setosa` и тот же UUID.
3. Найти этот UUID в реальном событии `prediction_completed` журнала сервера.
   Сопоставить браузер, JSON/заголовок ответа и запись лога.
4. Ввести `petal_width=0`. Ожидается понятное сообщение об ошибке `422` с UUID,
   без `[object Object]`; сопоставить его с `prediction_rejected`.
5. Открыть `/docs` и показать паспорт, новый ответ прогноза и ответы с ошибками.

Ajax использует адреса того же origin; отдельный CORS для локальной страницы не нужен.
Данные ответа выводятся безопасно через `textContent`. На сайте Pages остаётся
статическая документация; рабочая форма обслуживается самим FastAPI.

## Проверки и контейнеры

```powershell
py -3.11 -m pip install -r requirements.txt -r client/requirements.txt
py -3.11 -m pytest -q tests/test_variant4.py
py -3.11 -m pytest -q
docker compose up --build -d
docker compose ps -a
docker compose logs api client
py -3.11 scripts/check_api.py --base-url http://127.0.0.1:8080
```

Полный pytest включает прежние и новые тесты. Требуется проверить точный паспорт,
UUID клиента/сервера и неверный UUID, связь ответа с событием, `422` и безопасный
`500`, единый объект модели без повторного `load`/`fit`, HTML и новый OpenAPI.
Новая схема тестируется также через `scripts/tests/test_export_openapi.py`.

Dockerfile должен доставлять страницу и модуль UUID. Healthcheck использует
`model_loaded`; клиент проверяет и сохраняет `class_id`, `class_name`, `request_id`.
После контейнерной проверки запишите состояние API, exit code клиента и результат,
затем выполните `docker compose down`.

CI должен проверить PR и новый `main`; workflow Pages должен обновить опубликованную
схему после интеграции. Успех локальных тестов не подтверждает эти внешние действия.

## Рецензирование и сдача

По согласованному для этой работы исключению рецензирование выполняется как
учебный саморазбор автора в GitHub PR. Комментарий перечисляет проверенные
контракты, найденные проблемы и фактические исправления. Он явно обозначается
саморазбором; участие независимого рецензента не заявляется.
В Word-отчёт пользователь позднее вставляет фактические снимки и ссылки.
