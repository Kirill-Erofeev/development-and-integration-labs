# Подготовка к зачёту: 20 теоретических вопросов

Основа — методический документ «Теоретические вопросы к зачёту модуль 5.docx» и итоговая реализация Iris API, вариант 4, на Python 3.11. Вопросы о GitVerse применены к используемым в проекте GitHub, pull request и GitHub Pages; номера соответствуют порядку вопросов преподавателя. Код проекта и указанные официальные технические источники сверены 04.10.2026; этот материал объясняет реализацию и не заменяет протокол фактически выполненных проверок.

## 1. Чем исследовательский notebook отличается от производственного модуля и что переносится в проект?

Notebook удобен для последовательных экспериментов, промежуточных результатов и визуального исследования, но его работа может зависеть от состояния и порядка запуска ячеек. В программные модули переносят подготовку и проверку входных данных, обучение, сохранение и загрузку артефакта, предсказание и прикладную логику, чтобы вызывать их через понятные интерфейсы и проверять тестами. В нашем проекте обучение находится в `src/train.py`, загрузка и предсказание — в `src/model_service.py`, HTTP-слой — в `app/api.py`, а UUID и события — в `src/request_id.py`; рабочие notebook импортируют эти модули.

## 2. Почему нельзя обучать модель на каждый HTTP-запрос и когда её загружать?

Повторное обучение увеличивает задержку и расход ресурсов, а также смешивает подготовку модели с её применением и может менять результат между запросами. Доверенный готовый артефакт загружают при старте приложения и используют повторно; в FastAPI для этого подходит lifespan. В `app/api.py` lifespan один раз создаёт `ModelService` на процесс, сохраняет его в `app.state`, а `/predict`, `/model-info` и `/health` используют это общее состояние без `fit`. [Документация FastAPI о lifespan](https://fastapi.tiangolo.com/advanced/events/).

## 3. Какую роль выполняют Pydantic-модели в FastAPI?

Pydantic-модели задают поля, типы и ограничения данных, а FastAPI использует их для проверки тела запроса и построения документации. В нашем `PredictRequest` обязательны четыре положительных конечных числа: отсутствующее поле, строка вместо числа, `bool`, `NaN`, бесконечность и лишнее поле отклоняются до вызова предсказания. Например, `petal_width: 0` приводит к `422` с указанием ошибочного поля, а `PredictResponse` определяет поля `class_id`, `class_name` и `request_id`. [Описание тела запроса в FastAPI](https://fastapi.tiangolo.com/tutorial/body/).

## 4. Что входит в контракт REST API на примере `POST /predict`?

Контракт определяет метод и путь, формат и ограничения входных данных, значимые заголовки, структуру успешного ответа и правила ошибок. Наш `POST /predict` принимает JSON `{"sepal_length":5.1,"sepal_width":3.5,"petal_length":1.4,"petal_width":0.2}` и необязательный `X-Request-ID`. Ответ `200` содержит `class_id: 0`, `class_name: "setosa"` и UUID `request_id`, совпадающий с заголовком ответа и событием лога; корректный UUID клиента сохраняется канонически, отсутствующий или неверный заменяется UUIDv4. Контракт также предусматривает `400` для непрочитанного тела, `422` для ошибок JSON или признаков, `503` без модели и безопасный `500` при сбое прогноза.

## 5. Чем отличаются HTTP-коды `200`, `201`, `400`, `404`, `422` и `500`?

`200` означает успешную обработку, `201` — создание ресурса, `400` — ошибку клиентского запроса, `404` — отсутствие найденного ресурса, `422` — невозможность обработать содержимое запроса, `500` — внутреннюю ошибку сервера. [Семантика HTTP в RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-status-codes). В нашем API прогноз возвращает `200`, неизвестный маршрут — `404`, неверный UTF-8 тела — `400`, ошибки признаков или разбора JSON — `422`, а сбой предсказания — `500`; дополнительно `503` означает неготовую модель. `201` для обычного прогноза не нужен, потому что API не создаёт сохраняемый ресурс прогноза.

## 6. Что такое OpenAPI и чем `openapi.json` отличается от Swagger UI?

OpenAPI — машиночитаемое описание HTTP API: маршрутов, методов, параметров, схем данных и ответов; документ может быть представлен в JSON или YAML. [Спецификация OpenAPI](https://spec.openapis.org/oas/v3.1.0.html). `openapi.json` содержит сам контракт, а Swagger UI — веб-интерфейс, который загружает и отображает этот документ и при разрешённых настройках позволяет отправлять запросы. В проекте экспортируемая схема включает `/predict`, `/health` и `/model-info`, а статическая страница `docs/api/index.html` показывает её с локальными ресурсами Swagger UI.

## 7. Как FastAPI формирует схему и почему `app.openapi()` работает без веб-сервера?

FastAPI строит схему по зарегистрированным маршрутам, их параметрам, Pydantic-моделям и описаниям ответов; `app.openapi()` возвращает её как Python-структуру. [Механизм генерации OpenAPI](https://fastapi.tiangolo.com/how-to/extending-openapi/). Для этого вызова не требуется сетевой запрос или запущенный Uvicorn, если импорт приложения сам не выполняет лишних действий. В нашем проекте `scripts/export_openapi.py` импортирует `app.api:app` и сохраняет результат, не входя в lifespan, поэтому экспорт работает даже при несуществующем `ML_MODEL_PATH` и запрещённой загрузке модели.

## 8. Почему Swagger UI использует относительный `./openapi.json`?

Этот путь указывает на файл рядом со страницей Swagger UI и сохраняет правильную адресацию при размещении сайта в подкаталоге репозитория. Например, из `/development-and-integration-labs/api/` он ведёт к `/development-and-integration-labs/api/openapi.json`, тогда как `/openapi.json` обращается к корню домена и может дать `404`. Полный абсолютный URL тоже может работать, но жёстко привязывает страницу к конкретному адресу, поэтому в `docs/api/index.html` используется `url: "./openapi.json"`, а тест проверяет раздачу сайта под префиксом репозитория.

## 9. Почему опубликованный Swagger UI может показывать контракт без работающего `Try it out`?

Статическому Swagger UI достаточно схемы для отображения операций, но для запросов нужен отдельно работающий API с доступным адресом, подходящими настройками HTTP/HTTPS, CORS при другом origin и авторизацией, если она требуется. В нашей странице Pages выполнение специально отключено через `supportedSubmitMethods: []`, поскольку публикация документации не запускает FastAPI или модель. Проверять живой сервис следует через его собственный `/docs`, а статический сайт использовать для чтения контракта. [Настройка интерактивных методов Swagger UI](https://swagger.io/docs/open-source-tools/swagger-ui/usage/configuration/).

## 10. Почему фронтенд использует `fetch('/predict')` и как это связано с CORS?

Путь `/predict` берёт схему, хост и порт текущей страницы, поэтому не требует переписывать адрес API при переходе между локальным запуском и контейнером. Если страница и API имеют один origin — сочетание схемы, хоста и порта, — разрешать междоменные запросы через CORS не требуется. В нашем приложении `GET /` отдаёт `static/index.html`, а страница обращается к `/predict`, `/model-info` и `/health`; если перенести её на отдельный origin, вопрос CORS придётся решать отдельно. [Понятие origin и CORS в FastAPI](https://fastapi.tiangolo.com/tutorial/cors/).

## 11. Чем unit-тест отличается от интеграционного теста?

Unit-тест проверяет небольшую единицу логики с минимальными внешними зависимостями, а интеграционный — совместную работу нескольких компонентов. Для нашего проекта unit-примером является проверка, что `resolve_request_id()` канонизирует UUID или создаёт новый при неверном вводе. Интеграционный пример — запрос через `TestClient` к `/predict`, связывающий маршрутизацию, валидацию, загруженную модель, ответ и лог; запуск Uvicorn и проверка через реальный HTTP дополнительно проверяют сеть и процесс сервера.

## 12. Что проверять у `POST /predict` кроме успешного ответа?

Нужно проверить пропущенные и лишние поля, неверные типы, нулевые и отрицательные значения, нечисловые и бесконечные значения, повреждённый JSON, порядок признаков и понятные HTTP-ошибки без внутренних traceback. Для варианта 4 дополнительно проверяются передача и канонизация UUID, его генерация при отсутствии или неверном заголовке и совпадение идентификатора в JSON, заголовке и событии лога. В наших тестах есть `422` с UUID, назначенным до валидации, безопасные `400`, `500` и `503`, а также проверки единственной загрузки модели и отсутствия обучения между запросами.

## 13. Для чего нужен `/health` и как он применяется при развёртывании?

`/health` позволяет автоматически проверить доступность приложения и заданные проектом признаки его готовности перед зависимыми действиями. Наш ответ содержит `status: "ok"` и `model_loaded`, поэтому проверять только HTTP `200` недостаточно: при отсутствии модели флаг будет `false`. Healthcheck в `compose.yaml` проверяет оба значения, клиент ожидает `service_healthy`, а `scripts/check_api.py` использует готовность перед проверкой паспорта и прогноза.

## 14. Чем Docker image отличается от container и какие инструкции Dockerfile важны?

Image — набор неизменяемых слоёв с файлами и настройками для создания контейнера, а container — созданный на его основе экземпляр со своим состоянием, процессами при запуске и записываемым слоем. [Понятие Docker image](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/). В нашем Dockerfile `FROM python:3.11-slim` задаёт базовую среду, `WORKDIR` — рабочий каталог, `COPY` — перенос зависимостей, кода, модели и страницы, `RUN` — установку пакетов, `ENV` — настройки, а `CMD` — запуск Uvicorn. `EXPOSE 8000` документирует порт приложения, но доступ с хоста задаётся отдельно через публикацию порта контейнера.

## 15. Что решает Compose и чем отличаются `up` и `up --build`?

Compose описывает несколько сервисов, их сборку, сеть, переменные, тома и зависимости в одном файле, позволяя запускать согласованную конфигурацию. В нашем `compose.yaml` клиент обращается к `http://api:8000` по имени сервиса, ждёт здоровый API и сохраняет результат через подключённый каталог `results`. Обычный `docker compose up` создаёт и запускает сервисы, но не гарантирует пересборку образа после изменения исходников; `docker compose up --build` явно выполняет сборку перед запуском и при этом может использовать cache. [Команда Docker Compose up](https://docs.docker.com/reference/cli/docker/compose/up/).

## 16. Зачем нужны рабочая ветка, commit и merge request?

Рабочая ветка позволяет развивать отдельную задачу, не включая незавершённые изменения в основную линию проекта. Commit фиксирует связанное изменение и его происхождение, а запрос на слияние показывает общий diff, результаты проверок и обсуждение перед интеграцией. В GitHub такой запрос называется pull request; для варианта 4 в него логично включить согласованные изменения API, UUID, страницы, клиента, тестов и документации.

## 17. Зачем нужен ревьюер и чем полезен другой вариант задания?

Ревьюер независимо проверяет соответствие требованиям, корректность кода, тесты и понятность интерфейса и может заметить то, что автор привык пропускать. Одногруппник с другим вариантом полезен как внешний пользователь контракта: он оценивает ясность решения, не полагаясь на собственную реализацию той же задачи. Для нашего варианта предмет проверки — паспорт без пути к модели, связь UUID с реальным логом и обработка ошибок; выполненная самопроверка сама по себе не подтверждает участие независимого ревьюера.

## 18. Из каких этапов состоит типовой CI-конвейер API-проекта?

Checkout получает код нужной версии, установка зависимостей готовит среду, тесты проверяют поведение, сборка создаёт поставляемый результат, а публикация при необходимости передаёт его в реестр или среду размещения. В `.github/workflows/ci.yaml` job `check` устанавливает Python 3.11, проверяет синтаксис и выполняет pytest, после чего `build-image` последовательно собирает API и клиент. Эти образы в данном workflow не отправляются в реестр; документация публикуется отдельным `publish-api-docs.yaml`, а `delivery.yaml` выполняет учебный dry run и только печатает предлагаемые команды доставки.

## 19. Что такое артефакт CI/CD и как сборка документации передаётся между jobs?

Артефакт CI/CD — сохранённый результат работы конвейера, например готовый сайт, пакет или отчёт, который можно передать следующему этапу. В нашем job `build` каталог `${RUNNER_TEMP}/site` содержит Swagger UI, локальные ресурсы и сгенерированный `api/openapi.json`, а `actions/upload-pages-artifact` загружает его как артефакт Pages. Job `deploy` зависит от `build` и через `actions/deploy-pages` публикует этот результат, поэтому между jobs передаётся собранный сайт, а не предполагается общий локальный диск. [Пользовательские workflow GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## 20. Чем публикация Pages из ветки отличается от публикации из workflow?

При выборе публикации из ветки указывают ветку и каталог исходных файлов сайта; при выборе GitHub Actions шаги сборки и передачи артефакта определяются собственным workflow. Для нашего проекта подходит GitHub Actions: схема формируется вызовом `app.openapi()` во время сборки, проверяется и попадает в артефакт без коммита сгенерированного `openapi.json`. Так опубликованный контракт соответствует версии кода данного прогона; локальный каталог `site/` исключён из Git, а job публикации разрешён только для `main` и не запускается для pull request. [Выбор источника публикации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).
